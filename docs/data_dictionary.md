# Data dictionary

This summarizes current contracts; the [Protocol v5.2 Markdown](../protocols/experiment_protocol.md) defines the method. The PatchPrompt CSV is a candidate index, not a complete case source. Its `PR_Size` column is inherited metadata and unused for DIR screening.

## Screening

Stage A records are `dir-screening-v9` under `dir-tfg-v2`, written to distinct `screened_PA_PN_cases.csv` and `eligible_PA_PN_cases.csv` paths. `case_id` is stable; `source_case_id` links to the index. `Outcome_Class` selects the PA/PN population and later split strata, but is not a retrieval cue. `source_linkage_status` records administrative linkage as `established`, `conflicting`, or `unresolved`, with separate provenance and reason. `pr_conversation_match` records the separate Stage A manual judgment as `yes`, `no`, or `unresolved`, with reviewer provenance; it directly contributes to scientific eligibility. `conversation_available`, `temporal_anchor_available`, `first_generation_boundary_identifiable`, `duplicate_status`, `project_history_accessible`, and `historical_state_reconstructible` describe processability. `eligible` is `true`, `false`, or blank pending resolution; `eligibility_status`, `exclusion_reason`, `pending_reason`, and `processability_source` explain the scientific judgment. `stage_b_readiness_status` is separate operational metadata. A pending case may be `ready_for_stage_b` only when all packaging prerequisites pass and its pending reasons are limited to `first_generation_boundary_identifiable_unresolved` and `historical_state_reconstructible_unresolved`; any other pending reason blocks it. `stage_b_readiness_reason` records either `scientifically_eligible`, `pending_only_stage_c_tfg_deferred`, or explicit blockers. `changed_files`, `additions`, `deletions`, `changed_lines`, `pr_commits`, developer prompts, and conversation words are descriptive and cannot exclude by magnitude alone.

### Required and complementary Stage A fields

Protocol v5 §2.3 requires the neutral Case ID (`case_id`), PR URL/identifier (`pr_url`, with `repository`/`pr_number`), conversation reference (`conversation_url`), outcome class (`Outcome_Class`), conversation availability (`conversation_available`), temporal-anchor availability (`temporal_anchor_available`), preliminary boundary identifiability (`first_generation_boundary_identifiable`), PR/conversation match (`pr_conversation_match`), duplicate status (`duplicate_status`), project-history access (`project_history_accessible`), eligibility/status (`eligible`, `eligibility_status`), and exclusion reason (`exclusion_reason`). Stage A's boundary field records preliminary processability, not the authoritative first-generation `tFG` determined in Stage C. Existing retrieval/parsing statuses, precision/status/source, pending and provenance reasons, descriptive measures, and `stage_b_readiness_status` are complementary operational fields. None adds a numerical eligibility threshold.

`cases/manifests/case_mapping.csv` is a restricted researcher-only mapping derived from the authoritative source index and the current Stage A screened rows. Required protocol fields are `case_id`, `pr_url` (PR identifier), and `Outcome_Class` (PA/PN). `mapping_schema_version`, `source_case_id`, `conversation_id`, and `conversation_url` are complementary provenance fields. It does not replace `linkage/*.json` and is never Stage C model input. Stage A may access PR/project identity for administrative integrity, mapping, accessibility, duplicates, and preliminary processability. After Stage C, controlled historical access may resolve `S_i(tFG)` reconstructibility and eligibility; complete `H_i(tFG)` construction and substantive evidence discovery occur later under the frozen/split workflow.

`dir-source-linkage-correction-v1` records a verified correction to an inherited PR/conversation association without modifying the inherited source CSV. The overlay preserves the original and corrected URLs/IDs, stable case/source/PR binding, reviewer, timestamp, version, reason, and evidence reference. Current Stage A mapping and Stage B selection apply verified overlays before resolving conversation identity; historical reviews remain preserved separately.

## Post-Stage-C historical repository reconstruction

`historical-state-acquisition-v4` records the canonical repository identity, established focal PR, authoritative `tFG`, complete ordered focal commit lineage, applicable base lineage when needed, commit parents and trees, author/committer/effective timestamps, cutoff relations, temporal basis, topology checks, routing provenance, and exact materialization evidence. It contains no post-`tFG` commit message, patch, diff, or file content.

Effective time uses `committer_time` when usable, `author_time_fallback` only when committer time is unavailable, and remains unavailable otherwise. `historical-information-boundary-v4` exposes selected exact `S_i(tFG)` commit/tree and whether it came from the focal or applicable base lineage. Its status is `reconstructed_focal_state`, `reconstructed_base_state`, or `unresolved`; historical observability remains independent metadata. Base routing records either the resolvable PR base ref or deterministic focal-root external-parent/first-parent topology. All merge parents remain provenance. Complete recursive materialization must match the selected commit tree.

The scientific identifiers remain `post-stage-c-reconstruction-v4` and `post-stage-c-git-lineage-v4`. Stage F constructs the broader `H_i(tFG)` from `S_i(tFG)`; the boundary record does not represent complete Stage F historical information.

## Conversation and temporal records

Stage B preserves immutable `conversation-only-v1` packages and introduces `conversation-only-v2` under unchanged methodology `dir-tfg-v2`. V2 contains neutral case identity, temporal source, complete ordered visible turns, and deterministic `generated_technical_content_candidates`; project/outcome metadata remains absent. A Stage B candidate is not yet a scientific generated software artifact. Candidate kinds are `source_code`, `structured_xml_markup`, `shell_sequence`, `configuration_properties`, `structured_json`, and `unclassified_technical`; `container` independently records `markdown_fence` or `none`; completeness is `complete`, `fragment`, or `open_ended`. Incomplete candidates remain eligible for Stage C semantic selection.

Every V2 candidate uses `GTC_<event>_<start>_<end>_<hash-prefix>`, with inclusive/exclusive Python Unicode offsets into the owning visible turn and hashes of the exact substring and complete turn. `legacy_artifact_id` is required and nullable: it contains an `ARTIFACT_*` value only for exact V1 equivalence across case, response, event/record position, span, and hashes. `ARTIFACT_*` is V1 legacy provenance, not V2 identity. Candidates are response-local and no synthetic cross-response candidate is created.

The Stage C `conversation-draft-v3` shape supports preserved `conversation-extraction-v3`/`v4`/`v5` records. Current extraction-v6 uses `conversation-draft-v4`, Pass 1 prompt v4, Pass 2 prompt v3, and Pass 2 schema v2. For every C/S/V item, `source_turns` and `source_roles` are equal-length parallel arrays and each role corresponds positionally to its cited turn; repeated roles are repeated. Every evidence string must be textually attributable to at least one cited admissible turn. V4 also preserves the independent Pass 2 status and non-complete failure reason. Pass 1, family identity, boundary, `tFG`, and `dir-tfg-v2` are unchanged.

Stage C status is `complete`, `ambiguous`, `unresolved`, or `failed`. The record preserves independent `tC` and `tFG` anchors, `primary_repository_cutoff = tFG`, prompt/schema/input/model provenance, empty tool configuration, parsing/validation status, and an explicit declaration that eligibility was not updated. Post-C consumes this draft to resolve boundary identifiability and `S_i(tFG)` reconstructibility and to determine final scientific eligibility before Stage D sampling; it does not construct complete `H_i(tFG)`.

For future executions, `model_provenance.sdk_max_retries` records the configured OpenAI SDK automatic retry allowance. It does not report an observed retry or HTTP-attempt count. SDK retry allowance, application-level retry, and a separately authorized controlled development rerun are distinct; Stage C implements no application retry loop after semantic or deterministic failure. Historical records are not rewritten to add this field.

When Pass 2 was invoked but its result fails API completion, parsing, structured-contract validation, or deterministic item-provenance validation, the failed draft retains the invocation, prompt, schema, model, reasoning, and tool-policy provenance that is available. Rejected Pass 2 items are not copied into the accepted C/S/V fields. `parser_status` describes whether a returned payload was parsed; `validation_status` separately records whether the parsed result passed deterministic validation.

The same provenance rule applies to Pass 1. A rejected Pass 1 proposal never supplies the authoritative family, response, target, boundary, or `tFG`. Available invocation and response metadata remain in the failed draft, while a parsed rejected Pass 1 or Pass 2 payload is retained only in a non-authoritative `stage-c-rejected-output-v1` diagnostic sidecar. The sidecar is reproducibility/debugging material, explicitly records `authoritative = false` and `disposition = rejected_model_output`, and contains no credentials or complete request object.

`candidate_artifact_ids` is a required Pass 1 response field but its array may be empty. It is a model-generated auxiliary list, not the authoritative selected family. The current prompt and schema do not define whether it is exhaustive or require it to contain selected `artifact_ids`. Deterministic validation checks that every reported candidate ID exists, but does not require selected `artifact_ids` to be a subset and does not use this field to derive family identity, response, boundary, or `tFG`. An empty list therefore validates and means only that the model returned no candidate IDs; no stronger semantic conclusion is supported by the current contract.

For Protocol v5 records, `procedure_validation_status` describes whether the extraction procedure passed sample validation. `case_human_validation_status` distinguishes sampled human validated, sampled adjudicated, not sampled, and unresolved cases. `case_extraction_status` and `case_boundary_status` describe each case separately; `case_processability_status` records the structural check. `record_status = frozen` means an immutable output of the validated procedure, not individual human review.

`conversation_only_v2.schema.json` is the authoritative V2 model-view/candidate JSON contract. Deterministic validation additionally enforces source substring equality, response ownership, hashes, ID recomputation, unique spans/IDs, ordering, and legacy mapping rules that JSON Schema cannot express.

`case-linkage-v2` is restricted administrative metadata keyed by neutral `case_id`; it retains PR and source-conversation identity, including the Stage A canonical PR URL. It snapshots the established source-linkage and positive correspondence authorization used for packaging and references the authoritative Stage A manifest row and canonical correspondence-review JSON. Review rationale and evidence remain owned by Stage A. The linkage is not Stage C input. `chatgpt-source-v1` retains ordinary fresh/current-cache source payload bytes and provenance. `chatgpt-source-v2` represents an explicit offline import of preserved legacy raw response bytes and records the legacy paths, raw hash, canonical/final URLs, validated HTTP/retrieval status, and separate import timestamp. `chatgpt-source-v3` represents original historical HTTP bytes from `ChatgptSharing.HTMLContent` in the identity-matched PatchTrack ZIP member. It records ZIP/member/content hashes, exact source and sharing indexes, all qualifying snapshots, the earliest-valid selection rule, raw archival dates, and separate import time. The derived `Conversations` field is never authoritative.

The source archive records `source_origin` (`fresh`, `cached`, `legacy_cache_import`, or `archived_http_response`) and `retrieval_time_status`. HTTP cache entries retain their actual retrieval timestamp when known. An ordinary v1 cache entry without one uses `unknown_legacy_cache` and a blank `retrieved_at`; an explicit v2 legacy import uses `unknown_legacy_cache` and null `retrieved_at`; a v3 archived HTTP response uses `unknown_archive_timezone` and null `retrieved_at` because `DateOfAccess_raw` has no timezone. `lossless-conversation-v1` and `conversation-only-v1` remain unchanged. `stage_b_status = complete` means the archive checksum, normalized ordering/source positions, and allowlisted model view passed validation. `retrieval_failed`, `normalization_failed`, and `validation_failed` remain distinct incomplete outcomes.

`stage-b-summary-v1` is an operational CSV row contract for every Stage-A-ready case. It reports source and packaging status, validation, `tC`, failure reason, and `ready_for_stage_c`; it does not change Stage A scientific eligibility.

Stage B model-view isolation is structural and provenance-based. The model view must be the exact allowlisted deterministic derivative of the normalized conversation; administrative fields cannot be added independently. Repository names, URLs, PR references, paths, or similar strings genuinely present in user/assistant source text remain unchanged and retain conversation provenance.

`tC` (first developer prompt) and `tFG` (boundary immediately before the first artifact-bearing assistant response in the first snippet family) retain independent value, precision, status, and source. Current `primary_repository_cutoff` is `tFG`. Missing `tFG` is never filled from `tC`; date-only values do not become exact timestamps. `available_by_tC` and `available_by_tFG` remain separate (`YES`, `NO`, `UNCERTAIN`, `UNAVAILABLE`). Historical availability alone is not retrieval, relevance, or additional evidence.

`post-stage-c-eligibility-manifest-v2` is the active final eligibility ledger. It records reconstruction contract `post-stage-c-reconstruction-v4`, procedure `post-stage-c-git-lineage-v4`, target `historical_repository_state_at_tFG`, and the exact accepted reconstruction outcome. Its acquisition, boundary, and corpus-authority references trace `historical_state_reconstructible` to the canonical final evidence. Both focal and base reconstruction satisfy the criterion after the same temporal, topology, commit/tree, and complete-materialization validations. Historical observability and base-routing source remain provenance rather than separate eligibility criteria.

The stable Stage A, linkage, and Stage C records have versioned contracts. `frozen_conversation_v1.schema.json` and `repository_evidence_v1.schema.json` remain legacy `dir-tfg-v1` contracts and do not validate current Protocol v5 Stage C outputs. See [schemas/README.md](../schemas/README.md).

`case_integrity_status = ok` means only that implemented structural, identity, and duplicate checks found no conflict; it does not imply semantic correspondence. Stage A stores the identity-bound judgment in `cases/manifests/correspondence_reviews/<case_id>.json` for candidate/processable cases reaching manual screening. An index pair or archive association can establish source linkage but cannot automatically establish semantic correspondence. `project_history_accessible` is determined by a separate Git commit-object probe; `project_history_access_*` records mechanism, repository, tested object, status, source, and reason. The fetch permits up to 900 seconds, and a timeout is recorded explicitly as unresolved `fetch_timeout`. PR API accessibility is distinct from Git history accessibility. A successful Git probe does not prove `historical_state_reconstructible` at authoritative `tFG`.

The intermediate `stage_a_correspondence_review.csv` has stable identity, linkage, automated-status, evidence-policy/reference, judgment, and six manual provenance columns. Researchers edit only the judgment and six `pr_conversation_match_*` provenance columns. Blank judgments produce no canonical JSON and remain unresolved. Initial exports use `identifiers_and_source_linkage_only`. Completed semantic reviews may be prepared under `direct_share_reference_and_restricted_task_context_v1`, which binds each row to a checksum-verified `dir-correspondence-evidence-v1` packet under `cases/manifests/correspondence_evidence/`. Packets retain only an identity-bound PR share reference, minimal developer-authored task context, archive provenance when available, and the review observation. They explicitly distinguish archive support from reviewer attestation and are never Stage B/C input, Stage G input, or reconstruction evidence.

`conversation_turn_pattern` is derived only from the count of developer turns in a complete parsed conversation (`single_developer_prompt`, `multiple_developer_prompts`, or `unavailable`). It is descriptive and affects no Stage A decision. The v9 scientific manifest omits the former pilot lexical signals, cue lists, unassessed qualitative placeholders, and their producer provenance. Historical v6 outputs retain their original meaning and are not v9 records.
