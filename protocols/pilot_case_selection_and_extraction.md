# Developer Intent Reconstruction Experiment Protocol (Protocol v5 migration)

This Markdown is the repository's operational expression of the authoritative `Developer_Intent_Reconstruction_Experiment_Protocol_v5.docx` (Word §§1–17). Keep this filename until a separately approved rename. The current first-generation methodology version is `dir-tfg-v2`; older primary-`tC` records and `dir-tfg-v1` outputs are not equivalent. Existing `dir-screening-v3` manifests, smoke runs, cache, and the approximately-30-case `pilot_cases.csv` are preserved legacy/provisional results. They are not the Protocol v5 eligible corpus, validation sample, or discovery split. Do not regenerate them in place.

## 1. Population and Stage A screening

The inherited PatchPrompt analysis CSV at `data/raw/final_analysis_dataset_from_patchprompt_study.csv` is a candidate index and metadata source, not a complete raw-case source. `Outcome_Class` PA (Patch Applied) and PN (Patch Not Applied) define the generated-code candidate population. NE (No Existing Patch) and CL (Closed, a PR lifecycle class) are outside this population. PA/PN adoption status is never a retrieval cue or pre-evaluation success signal. Preserve PR and conversation links and inherited C/S/V scores for provenance. `PR_Size` is inherited, unchanged, and unused for DIR eligibility; its meaning is not inferred.

Screen **all** PA/PN candidates for concrete integrity, availability, temporal-anchor, and processability problems. Verify repository/PR/conversation identity; flag duplicates and unresolved mappings. An unrecoverable conversation, unusable temporal anchor, demonstrably unidentifiable first-generation boundary, inaccessible required project history, or demonstrably unreconstructible historical state may prevent eligibility. Distinguish `eligible`, `excluded`, and `pending_resolution`; missing proof is not evidence of a failed criterion. Preserve each decision's source, status, and reason. A link or current PR metadata alone does not prove historical reconstructibility. Stage A may identify a candidate first-generation event without doing full snippet-family construction or repository evidence discovery.

Keep changed-file count (unique PR diff paths), additions, deletions, changed lines (additions + deletions), PR commit count from the PR source/API, developer prompt count (user turns), and complete-conversation word count as **descriptive** measures only. No numerical size, length, prompt, line, file, or commit threshold excludes a valid case. Source C/S/V 0–2 scores are inherited metadata, not the later supplied-information categories. Future Stage A outputs use separate, versioned paths such as `cases/manifests/screened_PA_PN_cases.csv`, `eligible_PA_PN_cases.csv`, and `stage_a_summary.md`; report PA and PN counts before and after screening. The prior `screened_cases.csv` and `selection_summary.md` remain untouched legacy outputs.

## 2. Stage B conversation-only packaging

Preserve three distinct representations. The **retrieved source archive** retains the response payload and safe retrieval provenance for audit, not as Stage C input. The **lossless normalized conversation** retains every source conversation record in original order, original content, roles, code blocks, tool traces, timestamps, source identifiers/parent relations, first-generation responses, later turns, and source-to-normalized locations. Unsupported elements remain in the source archive with an explicit normalization limitation. The **Stage C model view** is derived from that normalized record: neutral stable case ID, source-supported temporal information, conversation-addressed developer/assistant turns, and conversation-derived turn/artifact provenance. It excludes administrative and project-side metadata. Full conversation content is preserved in the normalized record; once the boundary is known, supplied-C/S/V extraction is limited to the target prompt and permitted earlier turns. Preservation does not make the first artifact-bearing response or later turns admissible as supplied information.

The PR identifier, source Case ID, conversation reference, PA/PN administrative class, and integrity/linkage facts belong in a **restricted case-linkage record** associated through the same neutral DIR Case ID. It supports case matching and later Stage F acquisition but is never Stage C model input. Under the adopted interpretation, Word references to packaging the PR identifier refer to the complete research case/linkage record; Word §3's conversation-only rule controls what the Stage C model sees. Do **not** include repository name, PR URL/number, PA/PN, PR title/body, commits, issues, reviews, CI, changed files, final diff, or eventual integrated implementation in the Stage C model view. Source records that themselves contain tool-directed or project-side material remain in the restricted normalized/archive layers; they are not silently discarded or passed as supplied-C/S/V context.
The Stage B command prepares one explicitly named neutral case ID using the existing ChatGPT retriever. Its HTTP cache supports resumable acquisition; the separate source archive holds exact response bytes, checksum, actual original retrieval timestamp when known, fresh/cached origin, source URL, and allowlisted HTTP metadata. Missing timestamps in older cache entries stay unknown. Linkage, archive, normalized conversation, and model view are persisted separately with an incomplete/complete status; `complete` is recorded only after package validation. Existing packages are never overwritten by default. See [`pipeline/extraction/README.md`](../pipeline/extraction/README.md).

## 3. Stages C–E: first generation, supplied C/S/V, validation, freeze

Using the conversation-only package, identify the first snippet family, its first generated software artifact, the assistant response containing that artifact, and the immediately triggering developer prompt. The first-generation cutoff `tFG` is immediately **before** that response. Preserve candidate/uncertain status when source evidence cannot establish it. Fuller later snippet-family construction is a separate task. Stable case, turn, response, artifact, and family identifiers must remain traceable to raw conversation positions.

For the target prompt, use that prompt and only the permitted earlier conversation turns to extract Context, Specificity, and Verification **actually supplied** by the developer. Preserve each item's source turn and span. Exclude the first artifact-bearing response and every later turn. Never infer missing information, use PA/PN, inspect repository material, or enrich supplied C/S/V with response content. These information categories are distinct from inherited PatchPrompt numerical C/S/V scores.

After LLM-assisted conversation extraction, draw an approximately 30% PA/PN-stratified validation sample from the **actual eligible corpus**; do not hard-code a case count. Two independent PhD annotators, when the experiment is run, verify first family/artifact response, target prompt, cutoff, permitted turns, each supplied item's support/category/provenance, and absence of leakage. Preserve independent judgments before reconciliation. Compute agreement only for defined categorical judgments, not free-form wording. Human validation evaluates the reliability of the extraction **procedure** on the sample, not every case individually. Keep `procedure_validation_status`, `case_human_validation_status` (sampled and human validated; sampled and adjudicated; not sampled; or unresolved), `case_extraction_status`, and `case_boundary_status` distinct. If a systematic failure is found, version/revise the extraction procedure, identify affected records, regenerate affected extraction outputs, and revalidate as required. Do not label unsampled cases individually human validated. Word §14 separately leaves the size/statistic for later repository-evidence claim validation to be chosen after its annotation unit and workload are known.

Freeze and version conversation-side records **before** project-evidence analysis. Record stable IDs, target prompt, first-generation response/family, `tC`, `tFG`, allowed prior turns, supplied C/S/V with item provenance, extraction version, procedure and case statuses, methodology version, and `primary_repository_cutoff = tFG`. `frozen` means immutable output of the validated/versioned extraction procedure; it does **not** mean every case was individually human validated. An unsampled record may proceed when extraction succeeded, its boundary and structural/processability checks are resolved, the procedure passed validation, and no known systematic defect affects that record. Keep individually unresolved or failed records out of downstream assignment until resolved. Repository findings may add separate evidence but cannot rewrite the frozen account of what the developer supplied. Corrections require a new version retaining the prior one. The existing `frozen_conversation_v1.schema.json` is a legacy `dir-tfg-v1` contract, not a Protocol v5 validation contract.

## 4. Temporal anchors and admissibility

```text
tC  = date/timestamp of the first developer prompt in the conversation
tFG = boundary immediately before the assistant response containing the
      first generated artifact in the first snippet family
primary_repository_cutoff = tFG  # current dir-tfg-v2 experiment
```

For **both** anchors retain value, `date` versus `timestamp` precision, status (`exact`, `derivable`, `unresolved`, `unavailable`, or documented uncertainty), and source. Never fabricate time from a date, claim an exact repository snapshot from a date alone, overwrite known `tC`, or substitute `tC` for unresolved `tFG`. Older primary-`tC` and current primary-`tFG` results carry different methodology versions.

Where determinable, record `available_by_tC` and `available_by_tFG` independently. An item may be unavailable by `tC` yet available by `tFG` and pass the current temporal test; post-`tFG` evidence cannot. Uncertain timing stays uncertain. For conversational cues at target prompt `i`, use that prompt and only permitted earlier turns. Later conversation turns are inadmissible even when repository evidence is historical.

## 5. Split after conversation freeze

After the conversation extraction procedure is validated and applicable records are frozen, create a reproducible approximately 70% discovery / 30% held-out split, stratified by PA/PN where feasible. Split only the downstream-processable eligible corpus; individually unresolved critical boundaries, extraction failures, and cases affected by an unresolved systematic defect cannot be silently assigned. Unsampled cases can enter after passing the validated procedure and case checks above. Derive counts from that corpus. Store split assignments in manifests (`discovery_cases.csv`, `heldout_cases.csv`) without changing case IDs or duplicating raw packages. The split must precede repository-evidence analysis used to develop Retrieval Algorithm v1. Held-out project evidence cannot shape retrieval paths, rules, v1 design, or tuning.

## 6. Historical Project Information Space and Index

For case `i`, `H_i(t_i)` is the reproducibly searchable project information available at or before its frozen `t_i = tFG`. A compact **Historical Project Information Index** records stable identifiers, historical versions, source timestamps, temporal status, and retrieval references; it does not eagerly copy every payload. Include as supported: case ID and both anchors; repository boundary SHA, commit/parent timestamps and tree reference; PR identity, creation time and pre-boundary commits/comments/reviews only if the PR existed by `tFG`; historically available issue/work-item bodies/comments/linkage; pre-boundary CI run/job IDs, SHA, times and log references; and repository history accessible no later than `tFG`. A source created after `tFG` is unavailable to the primary experiment, even if useful later. Unknown boundary SHA stays unresolved.

Retain finite historical objects with provenance where practical. Keep large repository trees, full histories, diffs, CI logs, and long discussions as stable historical references and materialize relevant payloads on demand. `cases/raw/` remains an audit location and may contain future information; it is not conversation-side or SAFE input. Historical availability, successful retrieval, task relevance, and evidence status are separate judgments.

## 7. Stages G–H: discovery traces and Retrieval Algorithm v1

For each **discovery** case, start with only the frozen target prompt, permitted prior conversation, frozen supplied C/S/V, `tFG`, and valid `H_i(tFG)`. Starting cues may include names/paths, symbols, APIs, configuration, errors, diagnostics, domain concepts, requested behavior, schemas/example values, tests/expected output, and explicit acceptance conditions. A cue starts a search; it is not a presumption that information is missing.

Record retrieval trajectories as first-class traces: starting cue and turn provenance; searched source and operation; historical artifact ID/path/SHA/time; relevant fragment; why inspected; next justified operation; final additional information; C/S/V contribution; novelty beyond frozen conversation; and temporal verification. Distinguish source, retrieved artifact, relevant fragment, and retained evidence. Retain evidence only after assessing temporal validity, task relevance, additionality, C/S/V contribution, and uncertainty reduction. Same-PR or same-repository membership alone is insufficient. A case with no useful additional evidence is valid: retain searches attempted, stopping reason, and no-evidence result. Retrospective researcher inspection for method discovery never makes downstream material admissible to automated retrieval or reconstruction.

Derive recurring cue-to-operation-to-artifact-to-evidence mappings from discovery traces. Version and freeze Retrieval Algorithm v1, including source permissions, operation order/branches, temporal checks, retention conditions, and stopping rules, **before** held-out use. Do not tune on held-out cases.

## 8. Stage I: frozen retrieval and Evidence Engineering

On held-out cases, apply only frozen Algorithm v1. Keep retrieval separate from Evidence Engineering:

```text
Frozen retrieval -> Retrieved Evidence Index -> Evidence Selection
-> Semantic Reduction -> Deferred Payload Materialization
-> Payload Reduction -> Engineered Evidence E_i^eng
```

The compact retrieved-evidence index tracks evidence ID/type, historical artifact/version, reaching cue/operation, potential contribution, relationships, and materialization status. Semantic reduction asks which items matter and are nonredundant; payload reduction asks how much source content is needed. Materialize large payloads only after semantic selection unless bounded content is needed to decide. Keep complete historical pointers for audit. `E_i^eng` separates additional Context, Specificity, Verification, unresolved gaps/ambiguities, provenance, temporal basis, and relationships. Every statement requires admissible historical support.

## 9. Stages J–L: reconstruction, controlled generation, evaluation

Intent reconstruction receives only original target prompt, permitted pre-boundary conversation, frozen supplied C/S/V, and `E_i^eng`. Every added statement must be evidence-traceable; PA/PN and eventual integration stay hidden.

Run two controlled conditions with the **same current model, version, system instructions, decoding, and other controllable settings**: (1) original target prompt plus admissible prior conversation → `Code_original,current`; (2) reconstructed prompt plus admissible evidence-grounded context → `Code_reconstructed,current`. Historical ChatGPT output is observational history, not the controlled baseline.

Only **after both current outputs are fixed**, reveal the eventual integrated implementation for evaluation. It is observed downstream implementation, not literal ground truth of mental intent. Compare both outputs independently using suitable structural, behavioral, and human-judgment measures as defined later; textual similarity alone is insufficient. PA/PN can then be used for subgroup analysis.

## 10. RAW, SAFE, SEALED and reproducibility

RAW contains historical/audit material and may reveal the future. SAFE contains only reconstruction-admissible information under the frozen `tFG` method; SEALED contains future/outcome/evaluation-only information, including integrated implementation until Stage L. Preserve the ability to create a separately versioned `tC` sensitivity partition later. Never pass raw mixed packages or sealed material to conversation-side extraction, retrieval, Evidence Engineering, reconstruction, or generation.

Record source dataset checksum, stable case/object IDs, methodology/schema/extraction versions, temporal basis, retrieval traces, configuration/code version, package hashes, unresolved sources, and failures. Distinguish unavailable source from unsuccessful retrieval. Do not silently fill gaps, regenerate legacy output paths, or claim success when processability or provenance remains unresolved. Detailed Stage F–L formats should stabilize with the experiment; do not create speculative schemas merely to populate directories.
