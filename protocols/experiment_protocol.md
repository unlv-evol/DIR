# Developer Intent Reconstruction Study — Experiment Protocol

Case Screening, Conversation Extraction, Historical Project Evidence Discovery, and End-to-End Evaluation Protocol

This Markdown is the repository's operational expression of authoritative Protocol v5.1 in `Developer_Intent_Reconstruction_Experiment_Protocol_v5_1.docx`. The current first-generation methodology version is `dir-tfg-v2`. Protocol v5.1 adds Post-C reconstruction v2 and Stage F/J/L alignment while preserving historical v1 records. Preserve source material, retrieval provenance, and versioned research outputs.

## 1. Population and Stage A screening

The inherited PatchPrompt analysis CSV at `data/raw/final_analysis_dataset_from_patchprompt_study.csv` is a candidate index and metadata source, not a complete raw-case source. `Outcome_Class` PA (Patch Applied) and PN (Patch Not Applied) define the generated-code candidate population. NE (No Existing Patch) and CL (Closed, a PR lifecycle class) are outside this population. PA/PN adoption status is never a retrieval cue or pre-evaluation success signal. Preserve PR and conversation links and inherited C/S/V scores for provenance. `PR_Size` is inherited, unchanged, and unused for DIR eligibility; its meaning is not inferred.

Screen **all** PA/PN candidates for concrete integrity, availability, temporal-anchor, and processability problems. Verify repository/PR/conversation identity; flag duplicates and unresolved mappings. An unrecoverable conversation, unusable temporal anchor, demonstrably unidentifiable first-generation boundary, inaccessible required project history, or demonstrably unreconstructible historical state may prevent eligibility. Distinguish `eligible`, `excluded`, and `pending_resolution`; missing proof is not evidence of a failed criterion. Preserve each decision's source, status, and reason. A link or current PR metadata alone does not prove historical reconstructibility. Stage A may make a preliminary determination that a first-generation event appears identifiable for processability. Stage C authoritatively identifies its family, artifact, response, target prompt, and `tFG`; Stage A does not duplicate that semantic extraction.

Stage A defines and screens the PA/PN candidate corpus using two complementary activities within one stage: automated/administrative integrity and processability checks, and manual PR-conversation correspondence screening for 100% of candidate/processable cases reaching that activity. The manual judgment asks whether permitted information supports that the conversation and PR concern the same development task. It is a case-eligibility criterion, not downstream extraction validation. Scientific disposition (`eligible`, `excluded`, or `pending_resolution`) remains distinct from operational Stage B readiness. Stage B may package a pending case only when every prepackaging prerequisite is satisfied and its only pending reasons are preliminary first-generation boundary identifiability and `tFG`-dependent historical-state reconstructibility. Packaging does not promote scientific eligibility.

Operationally, the automated activity exports applicable cases to `cases/manifests/stage_a_correspondence_review.csv`. This restricted human-review interface contains stable case/PR/conversation identities, source-linkage provenance, automated status, an explicit evidence-policy/reference, and blank manual judgment/provenance cells. It excludes PA/PN and downstream or outcome information. Completed nonblank rows are validated and materialized as canonical `dir-correspondence-review-v1` JSON records under `cases/manifests/correspondence_reviews/`; blank judgments remain unresolved. Final Stage A screening consumes only those canonical records. The CSV is an interchange artifact within Stage A, not a new scientific stage or authoritative review store.

When a completed judgment uses direct share references and task context, prepare a checksum-bound `dir-correspondence-evidence-v1` packet under `cases/manifests/correspondence_evidence/`. The `direct_share_reference_and_restricted_task_context_v1` policy permits only the identity-bound PR share reference, minimal developer-authored conversation task context, archive provenance when available, and reviewer observation. Record `archive_exact_pair`, `archive_conflicting_reference`, or `reviewer_attestation_only` without upgrading weaker support. This administrative evidence can establish Stage A correspondence but is not historical reconstruction evidence: it cannot establish availability at a reconstruction cutoff, enter Stage B/C model input, seed Stage G, or be reused downstream without a separate admissibility determination. Exclude PA/PN, merge/adoption outcomes, final diffs, integrated implementations, assistant-generated solutions, and unrelated project content.

Stage A verifies source PR-conversation linkage using administrative provenance and flags demonstrable conflicts. Record source linkage separately as `established`, `conflicting`, or `unresolved`; PatchPrompt or PatchTrack association is provenance evidence but does not automatically prove semantic task correspondence. In the separate manual Stage A activity, record correspondence as `yes`, `no`, or `unresolved`: `yes` satisfies this criterion, `no` excludes with a concrete integrity reason, and `unresolved` remains `pending_resolution`. Review packets exclude PA/PN, final diffs, integrated implementations, adoption outcomes, downstream evaluation, Stage G evidence, and other outcome information. Mutable PR text is withheld or carries explicit temporal provenance. Basic correspondence screening does not require `tFG`. Test Git history accessibility separately by retrieving a known commit object through Git without inspecting project content. An inaccessible repository can be `no`; ambiguous fetch failure stays unresolved. PR API retrieval alone proves neither Git history access nor `tFG`-relative historical reconstructibility.

A demonstrably incorrect inherited conversation link may be corrected only through a verified, versioned `dir-source-linkage-correction-v1` overlay. Preserve the inherited CSV, original correspondence judgment, and prior evidence packet. Bind the overlay to the stable case/source/PR identities, record original and corrected share identities, reviewer, time, reason, and evidence reference, then reacquire and validate the corrected conversation and issue a new review version. Applying the overlay must not change the stable case ID or erase correction history.

Keep changed-file count (unique PR diff paths), additions, deletions, changed lines (additions + deletions), PR commit count from the PR source/API, developer prompt count (user turns), and complete-conversation word count as **descriptive** measures only. No numerical size, length, prompt, line, file, or commit threshold excludes a valid case. Source C/S/V 0–2 scores are inherited metadata, not the later supplied-information categories. Stage A intermediate smoke outputs use `data/intermediate/screening/`; full-corpus manifests use versioned records such as `cases/manifests/screened_PA_PN_cases.csv`, `eligible_PA_PN_cases.csv`, and `stage_a_summary.md`; report PA and PN counts before and after screening. Word §2.3 requires neutral Case ID, PR identifier, conversation reference, PA/PN class, conversation and temporal-anchor availability, preliminary boundary identifiability, PR/conversation match, duplicate status, project-history access, eligibility/status, and exclusion reason. The CSV retains complementary provenance, precision, retrieval, descriptive, and Stage B readiness fields without adding eligibility thresholds.

`conversation_turn_pattern` is a descriptive count category only. Stage A does not persist lexical prompt characteristics derived from the complete conversation as retrieval cues. Stage G must derive its own cues from the frozen target prompt, permitted earlier conversation, frozen supplied C/S/V, and other expressly permitted frozen inputs; old Stage A lexical outputs cannot seed, rank, filter, or otherwise influence retrieval or Algorithm v1.

## 2. Stage B conversation-only packaging

Preserve three distinct representations. The **retrieved source archive** retains the response payload and safe retrieval provenance for audit, not as Stage C input. The **lossless normalized conversation** retains every source conversation record in original order, original content, roles, code blocks, tool traces, timestamps, source identifiers/parent relations, first-generation responses, later turns, and source-to-normalized locations. Unsupported elements remain in the source archive with an explicit normalization limitation. The **Stage C model view** is derived from that normalized record: neutral stable case ID, source-supported temporal information, conversation-addressed developer/assistant turns, and conversation-derived turn/artifact provenance. It excludes administrative and project-side metadata. Full conversation content is preserved in the normalized record; once the boundary is known, supplied-C/S/V extraction is limited to the target prompt and permitted earlier turns. Preservation does not make the first artifact-bearing response or later turns admissible as supplied information.

The versioned `conversation-only-v2` model view represents deterministic Stage B **generated-technical-content candidates**, which are inputs to later semantic review rather than scientific artifact judgments. Candidate production `generated-technical-content-v2` includes source code, declarative XML/HTML/SVG resources, shell sequences, configuration/properties, structured JSON in bounded Markdown, and conservative technical fragments. Every candidate uses a `GTC_*` identifier derived only from its response event, exact Unicode source span, and raw-text hash. A required nullable `legacy_artifact_id` records an exact V1 span/provenance equivalence; `ARTIFACT_*` remains V1 provenance only. Candidates belong to one assistant response, retain exact source offsets and hashes, and never span responses. Incomplete candidates remain explicit and may later be selected when their relevance and family are determinate. Stage B does not assign first-family membership, target prompt, boundary, or `tFG`.

The PR identifier, source Case ID, conversation reference, PA/PN administrative class, and integrity/linkage facts belong in a **restricted case-linkage record** associated through the same neutral DIR Case ID. It supports case matching and later Stage F acquisition but is never Stage C model input. Its Stage A authorization trace references the authorizing screening row and canonical correspondence review while retaining only the established-linkage and positive-correspondence snapshots needed to audit progression. The revised Word protocol explicitly limits the Stage B conversation package supplied to Stage C to neutral DIR Case ID, source-supported conversation date/time, and complete conversation in original order. Stable source-position and artifact references are complementary conversation provenance. The restricted linkage record is research-administration infrastructure outside the conversation package. A deterministic researcher-only `cases/manifests/case_mapping.csv` records the protocol-required Case ID, PR identifier, and PA/PN outcome, with source/conversation identifiers for audit. Neither mapping nor linkage is Stage C input. Do **not** independently inject repository name, PR URL/number, PA/PN, PR title/body, commits, issues, reviews, CI, changed files, final diff, or eventual integrated implementation from administrative/project metadata into the Stage C model view. Identical strings genuinely present in the preserved source conversation remain conversation content. Isolation is established by provenance and deterministic structural derivation, not lexical absence. Source records that themselves contain tool-directed or project-side material remain in the restricted normalized/archive layers; they are not silently discarded or passed as supplied-C/S/V context.
Before Stage C, PR/repository identifiers may be accessed only for Stage A mapping, accessibility, integrity, duplicate, and preliminary processability checks. They never enter Stage B/C model-visible input or determine supplied C/S/V. After Stage C establishes `tFG`, the controlled Post-Stage-C workflow may reconstruct or evaluate only the historical state needed to resolve processability and eligibility. Substantive evidence discovery, retrieval-algorithm development, and intent reconstruction remain after Stage E freeze and the corpus split. The case mapping is generated from the authoritative source index and Stage A rows, never maintained independently.

The Stage B command prepares one explicitly named neutral case ID using the existing ChatGPT retriever. Its HTTP cache supports resumable acquisition; the separate source archive holds exact response bytes, checksum, actual original retrieval timestamp when known, fresh/cached origin, source URL, and allowlisted HTTP metadata. Missing timestamps in older cache entries stay unknown. Linkage, archive, normalized conversation, and model view are persisted separately with an incomplete/complete status; `complete` is recorded only after package validation. Existing packages are never overwritten by default. See [`pipeline/extraction/README.md`](../pipeline/extraction/README.md).

Historical `conversation-only-v1` packages and Stage C outputs remain immutable. V2 materialization uses the coexisting `stage_c_model_view_v2.json` filename. Stage C consumption of V2 is versioned as `conversation-extraction-v5` with Pass 1 prompt `dir-stage-c-first-generation-v4`; `stage-c-pass1-v2`, `conversation-draft-v3`, Pass 2, and temporal methodology `dir-tfg-v2` remain structurally unchanged.

An explicit offline legacy-cache import may use preserved raw public response bytes only when paired metadata validates public retrieval, HTTP 200, and the expected conversation identity. It must reparse the raw bytes with the current parser, record a distinct legacy-import origin and raw hash, preserve the unavailable retrieval time as unknown, and record import time separately. It cannot use derived evidence JSON as the source or fall through to network retrieval. Corpus orchestration preserves existing valid packages and reports packaging readiness separately from scientific eligibility.

An explicit offline archived-HTTP import may use only the original `ChatgptSharing.HTMLContent` bytes preserved in `data/raw/allPullRequestSharings.zip`. It requires exact share-ID and expected-PR association, HTTP 200, nonempty HTML, and a complete result from the current parser. Among qualifying snapshots it selects the earliest timestamp encoded in the archive-member filename, with archive member, source index, and sharing index as deterministic tie-breaks. The derived `ChatgptSharing.Conversations` list, screening evidence, parsed caches, correspondence evidence, and Stage A evidence cannot substitute for `HTMLContent`. Preserve ZIP, member, and embedded-content hashes; raw archival dates; null `retrieved_at`; `unknown_archive_timezone`; and a separate import time.

Production Stage B consumes the explicit Stage A readiness decision. Ready cases must have established source linkage, correspondence `yes`, a complete conversation and temporal anchor, unique identity, verified project-history access, and no demonstrated integrity or exclusion failure. Pending reasons other than `first_generation_boundary_identifiable_unresolved` and `historical_state_reconstructible_unresolved` block packaging. Stage B validates this allowlist defensively and preserves the incoming scientific status.

## 3. Stage C, Post-Stage-C resolution, Stage D validation, and Stage E freeze

Stage C uses two independent, tool-free OpenAI Responses API passes with the same explicitly configured model. Pass 1 receives the complete conversation-only Stage B model view and identifies the semantic membership of the first snippet family, its first generated software artifact, the assistant response containing that artifact, and the immediately triggering developer prompt. Conceptual family relationships may span assistant responses, but the authoritative first-generation family is response-local: it contains only coherent artifacts generated in the earliest assistant response that generates the conceptual family's first artifact. Later turns may aid relationship interpretation only; artifacts from later responses cannot enter the selected first-generation `artifact_ids`. It may supply a descriptive family label but does not create canonical identity. Deterministic code validates all returned identifiers and ordering, rejects any selected artifact whose `source_response_id` differs from the selected `response_turn_id`, derives the stable family identifier from the response-local selected artifact references, and derives `tFG` immediately **before** that response. Preserve ambiguous, unresolved, and failed status rather than fabricating a selection or timestamp. Stable case, turn, response, artifact, and family identifiers remain traceable to raw conversation positions.

The current execution configuration explicitly permits up to two OpenAI SDK automatic retries for retryable transport/provider failures (`DIR_STAGE_C_MAX_RETRIES=2`). This bounded SDK setting is execution provenance and does not alter the scientific extraction method. Stage C adds no application-level retry after semantic, deterministic, provenance, or human-validation failure. A controlled rerun requires separate authorization, a distinct run identifier, and a distinct output.

For `conversation-draft-v3` / `conversation-extraction-v3`, the family identifier algorithm is frozen as `FGF_` plus the first 24 lowercase hexadecimal characters of SHA-256 over compact, key-sorted UTF-8 JSON containing `artifact_ids` and `case_id`. Before serialization, selected artifacts are ordered by `response_event_index`, `order_within_response`, and `artifact_id`. Changing this algorithm requires a new explicitly versioned contract.

Pass 2 receives only conversation turns strictly before the first-generation boundary. Both user and assistant turns in that window are admissible conversation-side evidence, and provenance preserves the originating role. Extract textual Context, Specificity, and Verification actually available in that window as atomic normalized statements with source turns, roles, and supporting evidence. C/S/V are information categories, not scores. Exclude the first artifact-bearing response and every later turn. Never infer missing information, use PA/PN, inspect repository material, or enrich supplied C/S/V with response content. During Stage C, model-accessible web, file, repository, code-interpreter, and other external tools are disabled; Stage C operates exclusively on the DIR-supplied conversation evidence.

Provenance is represented positionally. For every extracted Context, Specificity, or Verification item, `source_turns` and `source_roles` are parallel arrays of equal length: `source_roles[i]` records the actual originating role of `source_turns[i]`. When multiple cited turns have the same role, repeat that role for every corresponding turn. Every supporting `evidence` entry must remain textually attributable to at least one of the item's cited admissible source turns. Extraction records preserve the Pass 2 status and its non-complete `failure_reason` independently from the overall Stage C status.

Under `dir-stage-c-csv-extraction-v2` / `conversation-extraction-v4`, normalization preserves descriptive versus normative modality. Symptoms, failures, historical behavior, environment, branch, or platform differences, and diagnostic observations normally remain Context. They qualify as Verification only when an admissible source explicitly supplies a desired condition, expected outcome or behavior, correctness condition, check or test, assertion, acceptance condition, verification activity, or prescriptive guidance. Do not convert `is`, `was`, `happened`, or `observed` into `should`, `must`, or a requirement on a future fix without source support. When a passage contains both an observation and an explicit expectation, keep them atomic and separately supported when extracted. This development-pilot clarification retains the three C/S/V categories, Pass 1, `tFG`, and `dir-tfg-v2` unchanged.

The Post-Stage-C Historical Processability / Eligibility Resolution workflow occurs immediately after Stage C and before Stage D. It consumes the authoritative boundary and `tFG`, resolves `first_generation_boundary_identifiable`, and determines whether the minimum repository boundary needed by the later experiment can be historically identified and reproducibly validated. It resolves `historical_state_reconstructible` and remaining deferred criteria and determines final scientific eligibility. It is a gate/workflow, not another lettered stage. It does not construct the complete `H_i(tFG)`, perform broad issue/CI/discussion discovery, assess task relevance, or reconstruct intent. Stage C itself never promotes `pending_resolution` to `eligible`.

Historical `post-stage-c-reconstruction-v1` defined its target as the historically evidenced focal-PR base applicable at `tFG`; its records and eight-case pilot retain that meaning. Current `post-stage-c-reconstruction-v2` instead defines `R_i(tFG)` as the historically justified repository revision representing the project baseline relevant to the focal development task at the first-generation boundary. `R_i(tFG)` must be linked to the focal development context by admissible historical evidence, exist at or before `tFG`, avoid outcome information, and be reproducibly materializable with immutable object and tree validation. It is never selected merely because it is currently fetchable, a current PR base/default tip, the latest or nearest commit before `tFG`, an eventual merge base, or part of the integrated implementation.

Conceptually, `H_i(tFG) = {R_i(tFG), PR_i^{<=tFG}, Issues_i^{<=tFG}, CI_i^{<=tFG}, Discussion_i^{<=tFG}, History_i^{<=tFG}}`. Components have independent status and enter only when historically available. The PR may provide evidence for `R_i(tFG)` when it existed by the boundary, but `R_i(tFG)` is not definitionally a PR base and PR existence is not required. If `PR created_at > tFG`, record `pr_existed_by_tFG = false` and the PR component as `unavailable_by_tFG`; establish `R_i(tFG)` independently rather than treating the case as an automatic failure or using later PR state retroactively.

Keep historical identity/linkage, temporal applicability, authoritative `R_i(tFG)`, Git materialization, and immutable object/tree validation in that order. Materialization validates an already justified target and cannot establish identity retroactively. Exact timestamp equality is admissible under `historical_timestamp <= tFG`; same-date ordering at date-only precision remains unresolved without independent ordering evidence. `historical_state_reconstructible = yes` requires established identity and focal-development linkage, temporal applicability, immutable object validation, deterministic repository/tree materialization, retained provenance, and no outcome information. `no` requires affirmative scientific evidence. Missing credentials, rate limits, transport failure, timeout, deletion/private transition, or one missing remote remain unresolved absent such evidence.

Apply the v2 development-baseline hierarchy: **B1**, direct historical pre-`tFG` revision evidence linked to the focal development state; **B2**, a deterministic immutable Git derivation from a historically linked focal revision; **B3**, historically versioned project/PR/task/branch metadata that establishes the relevant baseline, with PR evidence allowed only when the PR existed by `tFG`; **B4**, archived historical derivation leads requiring explicit validation; and **B5**, supporting-only present-day metadata, current reachability/default state, temporal proximity, or commit timestamp. B4 is not automatically authoritative, and B5 cannot establish `R_i(tFG)` independently. Retain the candidate and authoritative SHA, source/time/precision, focal linkage, derivation rule and inputs, immutable relationships, validations, tree identity, evidence hash/provenance, conflicts, and adjudication.

Retain every target-identity claim and its hierarchy level, source identity, historical time and precision, relation to `tFG`, retrieval time, content hash where applicable, provenance, asserted base SHA, and status. When sufficient stronger historical evidence identifies SHA A and current metadata reports SHA B, retain A and record B as later/supporting provenance. Comparably authoritative historical claims that disagree remain `target_identity_status = ambiguous` and `historical_state_reconstructible = unresolved`; current fetchability cannot break the tie. If only current metadata or Git evidence exists, identity remains unresolved rather than scientifically `no`.

Human adjudication may compare retained claims, apply the frozen hierarchy, assess provenance, and verify deterministic derivations. It may not invent a state, use final outcome or implementation, infer identity from post-`tFG` substantive evidence, or choose the easiest candidate to fetch. Preserve the case, candidate states, evidence references, hierarchy levels, decision, rationale, adjudicator status, timestamp, and contract version.

Stage D validates the Stage C conversation extraction after final scientific eligibility resolution. Draw an approximately 30% PA/PN-stratified validation sample from the **actual eligible corpus**; do not hard-code a case count. Two independent PhD annotators, when the experiment is run, verify first family/artifact response, target prompt, cutoff, permitted turns, each supplied item's support/category/provenance, and absence of leakage. Preserve independent judgments before reconciliation. Compute agreement only for defined categorical judgments, not free-form wording. Human validation evaluates the reliability of the extraction **procedure** on the sample, not every case individually. Keep `procedure_validation_status`, `case_human_validation_status` (sampled and human validated; sampled and adjudicated; not sampled; or unresolved), `case_extraction_status`, and `case_boundary_status` distinct. If a systematic failure is found, version/revise the extraction procedure, identify affected records, regenerate affected extraction outputs, and revalidate as required. Do not label unsampled cases individually human validated. Adjudicated corrections replace the authoritative extraction only through a new retained version before Stage E freeze.

Freeze and version conversation-side records **before substantive project-evidence discovery**. The preceding Post-Stage-C repository access is limited to resolving historical-state processability and eligibility at `tFG`; it cannot rewrite Stage C supplied C/S/V. Record stable IDs, target prompt, first-generation response/family, `tC`, `tFG`, allowed prior turns, supplied C/S/V with item provenance, extraction version, procedure and case statuses, methodology version, and `primary_repository_cutoff = tFG`. `frozen` means immutable output of the validated/versioned extraction procedure; it does **not** mean every case was individually human validated. The strict resolved-case gate is applied before Stage D sampling, and Stage E freezes the validated/adjudicated authoritative records. Keep individually unresolved or failed records out of validation sampling, freeze, and downstream assignment. Corrections require a new version retaining the prior one.

## 4. Temporal anchors and admissibility

```text
tC  = date/timestamp of the first developer prompt in the conversation
tFG = boundary immediately before the assistant response containing the
      first generated artifact in the first snippet family
primary_repository_cutoff = tFG  # current dir-tfg-v2 experiment
```

For **both** anchors retain value, `date` versus `timestamp` precision, status (`exact`, `derivable`, `unresolved`, `unavailable`, or documented uncertainty), and source. Never fabricate time from a date, claim an exact repository snapshot from a date alone, overwrite known `tC`, or substitute `tC` for unresolved `tFG`. Results must carry the methodology version and primary cutoff used.

Where determinable, record `available_by_tC` and `available_by_tFG` independently. An item may be unavailable by `tC` yet available by `tFG` and pass the current temporal test; post-`tFG` evidence cannot. Uncertain timing stays uncertain. For conversational cues at target prompt `i`, use that prompt and only permitted earlier turns. Later conversation turns are inadmissible even when repository evidence is historical.

## 5. Stage F corpus assignment and historical information construction

Stage F contains two activities. **F1 — Corpus Assignment** creates a reproducible approximately 70% discovery / 30% held-out split, stratified by PA/PN where feasible, after eligibility and Stage D/E validation/freeze. Split only the downstream-processable eligible corpus. **F2 — Historical Information Construction** builds complete `H_i(tFG)` for frozen eligible cases, consuming the authoritative `R_i(tFG)` established during Post-C and never silently selecting a replacement boundary. Store assignments without changing case IDs. Held-out project information cannot shape retrieval paths, rules, v1 design, or tuning.

## 6. Historical Project Information Space and Index

For case `i`, `H_i(t_i)` is reproducibly searchable project information available at or before frozen `t_i = tFG`. A compact Historical Project Information Index records `R_i(tFG)` as the repository anchor, its tree/history references, and independently statused PR, issue/work-item, CI, discussion/review, and other permitted project components. Include PR state only when the PR existed by `tFG`. Each component records historical availability, temporal provenance, retrieval/materialization status, and source provenance. Stage F establishes historical availability; it does not determine task relevance.

Retain finite historical objects with provenance where practical. Keep large repository trees, full histories, diffs, CI logs, and long discussions as stable historical references and materialize relevant payloads on demand. `cases/raw/` remains an audit location and may contain future information; it is not conversation-side or SAFE input. Historical availability, successful retrieval, task relevance, and evidence status are separate judgments.

## 7. Stages G–H: discovery traces and Retrieval Algorithm v1

For each **discovery** case, start with only the frozen target prompt, permitted prior conversation, frozen supplied C/S/V, `tFG`, and valid `H_i(tFG)`. Starting cues may include names/paths, symbols, APIs, configuration, errors, diagnostics, domain concepts, requested behavior, schemas/example values, tests/expected output, and explicit acceptance conditions. A cue starts a search; it is not a presumption that information is missing.

Derive each cue from those permitted frozen inputs. Complete-conversation Stage A characteristics, including historical lexical screening fields, cannot seed, filter, rank, or tune Stage G retrieval or Algorithm v1.

Record retrieval trajectories as first-class traces: starting cue and turn provenance; searched source and operation; historical artifact ID/path/SHA/time; relevant fragment; why inspected; next justified operation; final additional information; C/S/V contribution; novelty beyond frozen conversation; and temporal verification. Distinguish source, retrieved artifact, relevant fragment, and retained evidence. Under Word §8.4, candidate additional evidence must concern the target programming task, add information beyond the frozen conversation, and contribute Context, Specificity, Verification, or a combination. Temporal availability by `tFG` is a separate mandatory global admissibility rule. Uncertainty reduction and evidence strength may be recorded as complementary analytic judgments; neither is an extra eligibility gate. Same-PR or same-repository membership alone is insufficient. A case with no useful additional evidence is valid: retain searches attempted, stopping reason, and no-evidence result. Retrospective researcher inspection for method discovery never makes downstream material admissible to automated retrieval or reconstruction.

Derive recurring cue-to-operation-to-artifact-to-evidence mappings from discovery traces. Version and freeze Retrieval Algorithm v1, including source permissions, operation order/branches, temporal checks, retention conditions, and stopping rules, **before** held-out use. Do not tune on held-out cases.

## 8. Stage I: frozen retrieval and Evidence Engineering

On held-out cases, apply only frozen Algorithm v1. Keep retrieval separate from Evidence Engineering:

```text
Frozen retrieval -> Retrieved Evidence Index -> Evidence Selection
-> Semantic Reduction -> Deferred Payload Materialization
-> Payload Reduction -> Engineered Evidence E_i^eng
```

The compact retrieved-evidence index tracks evidence ID/type, historical artifact/version, reaching cue/operation, potential contribution, relationships, and materialization status. Semantic reduction asks which items matter and are nonredundant; payload reduction asks how much source content is needed. Materialize large payloads only after semantic selection unless bounded content is needed to decide. Keep complete historical pointers for audit. `E_i^eng` separates additional Context, Specificity, Verification, unresolved gaps/ambiguities, provenance, temporal basis, and relationships. Every statement requires admissible historical support.

## 9. Stages J–L: reconstruction, controlled generation, evaluation

Stage J has two substeps. **J1 — Structured Intent Record** combines only the original target prompt, admissible prior conversation, frozen supplied C/S/V, and `E_i^eng`. It separates developer-stated information, project-recovered evidence, cautious inference, and unresolved information; supported fields may include goal, affected entities, constraints, expected behavior, verification evidence, and unresolved questions. Every substantive recovered claim retains provenance. Stage J cannot reopen repository sources, search `H_i(tFG)`, alter Stage I selection, add new evidence, or use outcomes. **J2 — Evidence-Grounded Prompt Reconstruction** produces the reconstructed prompt from that record while preserving uncertainty.

Run two controlled conditions with the **same current model, version, system instructions, decoding, and other controllable settings**: (1) original target prompt plus admissible prior conversation → `Code_original,current`; (2) reconstructed prompt plus admissible evidence-grounded context → `Code_reconstructed,current`. Historical ChatGPT output is observational history, not the controlled baseline.

Stage L has two evaluation components. After both Stage K outputs are fixed but before outcome revelation, **L1 — Intent-Record Fidelity Evaluation** assesses support, preservation of the stated task, stated/recovered/inferred separation, provenance completeness, uncertainty handling, unsupported intent, and omission or distortion. Freeze L1 before revealing the eventual integrated implementation. Only after both outputs and L1 are fixed may the reveal occur. **L2 — Generation-Effectiveness Evaluation** then compares the two generated-code conditions under the evaluation protocol. Fidelity and improvement remain separate conclusions; neither proves the other. PA/PN may then be used for subgroup analysis.

## Immediate conversation-side deliverables

The current deliverables are `screened_PA_PN_cases.csv`, `eligible_PA_PN_cases.csv`, lossless conversation packages for applicable processable cases, researcher-only `case_mapping.csv`, and documentation of fields and exact screening/packaging steps. Source archives, normalized conversations, Stage C model views, package statuses, linkage records, caches, and version metadata are complementary reproducibility layers. No substantive project evidence, final diff, or integrated implementation is extracted for conversation-side analysis.

## 10. RAW, SAFE, SEALED and reproducibility

RAW contains historical/audit material and may reveal the future. SAFE contains only reconstruction-admissible information under the frozen `tFG` method; SEALED contains future/outcome/evaluation-only information, including integrated implementation until Stage L. Preserve the ability to create a separately versioned `tC` sensitivity partition later. Never pass raw mixed packages or sealed material to conversation-side extraction, retrieval, Evidence Engineering, reconstruction, or generation.

Record source dataset checksum, stable case/object IDs, methodology/schema/extraction versions, temporal basis, retrieval traces, configuration/code version, package hashes, unresolved sources, and failures. Distinguish unavailable source from unsuccessful retrieval. Do not silently fill gaps, overwrite existing research outputs, or claim success when processability or provenance remains unresolved. Detailed Stage F–L formats should stabilize with the experiment; do not create speculative schemas merely to populate directories.
